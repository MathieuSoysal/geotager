## 3. Question 2 — piexifjs : écriture GPS, endianness, XMP/IPTC, maintenance, limites

J'ai téléchargé et **lu le code source** de `piexifjs@1.0.6` (`piexif.js`, 78 998 octets).

**Écrit-il vraiment le GPS IFD en JPEG ? OUI.** Preuve dans `that.dump()` :
```js
if (("GPS" in exif_dict) && (Object.keys(exif_dict["GPS"]).length)) {
    zeroth_ifd[that.ImageIFD.GPSTag] = 1;   // pose le pointeur 0x8825 dans l'IFD0
    gps_is = true;
    gps_ifd = exif_dict["GPS"];
}
```
Un helper dédié existe : `that.GPSHelper.degToDmsRational(degFloat)` → `[[deg,1],[min,1],[sec,100]]`, et `dmsRationalToDeg(dmsArray, ref)`. API publique : `load`, `dump`, `insert`, `remove`, `TAGS`, `ImageIFD`, `GPSIFD`, `GPSHelper`.

**Endianness.** Asymétrie importante :
- **Lecture : les deux ordres sont gérés.** `exifReader.endian_mark` vaut `"<"` ou `">"` selon `II`/`MM`, et toutes les lectures passent par `unpack(this.endian_mark + …)`.
- **Écriture : TOUJOURS big-endian, en dur.** Dans `dump()` :
  ```js
  var header = "Exif\x00\x00\x4d\x4d\x00\x2a\x00\x00\x00\x08";
  //                        ^^^^^^^^ 0x4D4D = "MM" = big-endian
  ```
  → Un JPEG d'origine little-endian (Canon, la plupart des Nikon) sera **réécrit en big-endian**. Conforme à la spec, mais change l'octet-à-octet du fichier ; à documenter si vous promettez une modification « minimale ».

**XMP / IPTC : NON, aucun des deux.** Vérifié par comptage sur le source : `grep -c -i xmp` → **0**, `grep -c -i iptc` → **0**, marqueur APP13 → **0**. piexifjs ne touche que l'APP1:Exif.

**Maintenance : abandonnée.**
- **Dernière version stable 1.0.6 du 2019-06-21** (MESURE registre).
- **Dernier commit : 21 juin 2019** (« ver. 1.0.6 »), page `/commits/master` lue.
- Une branche v2 morte : `dist-tags.beta = 2.0.0-beta.9`, publiée **2019-11-07**, jamais stabilisée. Le README annonce toujours « We are implementing v2.0 ».
- **18 issues ouvertes**, dont « Is v2.0 still to be released? » (2020-07-07) et « **Dead** » (2020-11-16). Activité la plus récente : 2025-08-20.
- Le source déclare `that.version = "1.0.4"` alors que le paquet est en 1.0.6 — incohérence de release.
- **Alternative recommandée : `piexif-ts@2.1.0`** (MIT, 2024-03-10, 80 004 o / **12 374 o gzip**), port TypeScript du même code, plus récent de 5 ans, sans dépendance. Ou `@innei/piexif-ts@2.1.2` (MIT, 2025-06-11) — mais celui-ci déclare `vitest` en **dépendance de production**, ce qui est un défaut de packaging.

**Limitations connues (analyse du source + issues) :**

| Limite | Gravité | Détail |
|---|---|---|
| **API en *binary string*, pas ArrayBuffer** | **Haute** | `load(data)` attend une chaîne latin-1 (`data.slice(0,2) != "\xff\xd8"`). Depuis un `File`, il faut `FileReader.readAsDataURL` ou une conversion `Uint8Array`→`String.fromCharCode`. **~2× la mémoire de l'image, et un coût CPU sur le thread** — à isoler impérativement dans le Web Worker. |
| **APP12/APP13 (Photoshop/IPTC) : préservés** ✅ | Faible | Bonne nouvelle, contre l'intuition. `mergeSegments()` ne remplace **que** le premier segment `\xff\xe1` dont les octets 4–10 valent `"Exif\x00\x00"` ; tous les autres segments sont réémis tels quels via `segments.join("")`. Les APP13/IPTC et les XMP APP1 survivent. |
| **Insertion en tête si pas d'EXIF préexistant** | Moyenne | `segments = [segments[0], exif].concat(segments.slice(1))` → l'APP1 Exif est inséré **juste après SOI, donc AVANT un éventuel APP0 JFIF**. Techniquement non conforme à JFIF (APP0 doit être premier). Toléré par la quasi-totalité des décodeurs, mais ExifTool le signale. |
| **Segments APP1 Exif multiples : supprimés** | Faible | Les occurrences surnuméraires sont retirées (`additionalAPP1ExifSegments`). Comportement correct. |
| **JPEG multi-images (MPF, Samsung/Apple trailers)** | Moyenne | `splitIntoSegments` s'arrête à SOS (`\xff\xda`) et pousse **tout le reste en un seul bloc** : les données après EOI sont **conservées**, mais **les offsets MPF de l'APP2 ne sont pas recalculés**. Si l'APP1 Exif change de taille, les pointeurs MPF vers la 2ᵉ image deviennent faux. **NON VÉRIFIÉ empiriquement** — à tester avec une photo iPhone en mode Portrait. |
| **Limite 64 Ko de l'APP1** | Moyenne | Aucune gestion de l'EXIF étendu. Une grosse vignette + MakerNote peut dépasser 65 533 octets → JPEG corrompu silencieusement. **NON VÉRIFIÉ** — à tester. |
| **Pas d'écriture de l'offset d'IFD suivant** | Moyenne | Issue #… « Not writing offset of next IFD » (2019-09-10), ouverte. |
| **Perte de champs en manipulant le GPS** | Moyenne | Issue « Lost/modified fields setting GPS to {} » (2019-08-01), ouverte. |
| **Rotation cassée après effacement EXIF** | Attendu | Issue (2020-08-14) : supprimer l'EXIF supprime `Orientation`. Comportement normal, mais **piège UX majeur pour Geotagor** : « supprimer la position » ne doit PAS appeler `remove()` (qui vide tout l'EXIF) mais réécrire l'IFD sans le GPS IFD. |
| **MakerNotes** | Haute | Les MakerNotes contiennent des offsets absolus dans le TIFF. Réécrire l'IFD0 les déplace → **MakerNotes corrompues**. C'est un défaut structurel de tous les réécrivains naïfs, pas propre à piexifjs. **NON VÉRIFIÉ** pour piexifjs spécifiquement — test indispensable (photo Canon CR-…/JPEG, Nikon, Sony). |

## 5. Question 4 — Écriture XMP

**Il n'existe pas de bibliothèque JS générique d'écriture XMP.** Le seul candidat, `@mtillmann/jpeg-xmp-writer@0.0.6` (ISC), est limité au JPEG, en version 0.0.x, sans dépôt déclaré. **Il faudra le construire à la main.** C'est acceptable : le XMP est du XML plat, et pour du GPS on n'a besoin que d'un `rdf:Description` avec des attributs.

**Constantes vérifiées** — toutes extraites du **source d'ExifTool** (`lib/Image/ExifTool/XMP.pm` et `WriteXMP.pl`, lus intégralement) :

```perl
# XMP.pm, lignes 117-152
exif         => 'http://ns.adobe.com/exif/1.0/'
exifEX       => 'http://cipa.jp/exif/1.0/'
photoshop    => 'http://ns.adobe.com/photoshop/1.0/'
xmp          => 'http://ns.adobe.com/xap/1.0/'
x            => 'adobe:ns:meta/'
Iptc4xmpCore => 'http://iptc.org/std/Iptc4xmpCore/1.0/xmlns/'
Iptc4xmpExt  => 'http://iptc.org/std/Iptc4xmpExt/2008-02-29/'

# WriteXMP.pl, lignes 43-50 (verbatim)
my $pktOpen   = "<?xpacket begin='\xef\xbb\xbf' id='W5M0MpCehiHzreSzNTczkc9d'?>\n";
my $rdfOpen   = "<rdf:RDF xmlns:rdf='http://www.w3.org/1999/02/22-rdf-syntax-ns#'>\n";
my $rdfClose  = "</rdf:RDF>\n";
my $xmpClose  = "</x:xmpmeta>\n";
my $pktCloseW = "<?xpacket end='w'?>";   # writable

# ExifTool.pm, lignes 1241-1242 : signature du segment APP1 JPEG

$xmpExtAPP1hdr = "http://ns.adobe.com/xmp/extension/\0";
```

**Format des coordonnées XMP** — c'est le point que tout le monde rate. Ce n'est **PAS** un décimal. ExifTool (`GPS.pm`, `sub ToDMS`, branche d'écriture `doPrintConv eq '2'`) utilise :

```perl
$fmt = "%d,%.8f$ref";   # use XMP format with 8 decimal minutes
```

→ **degrés entiers, virgule, minutes décimales (8 décimales), puis N/S/E/W collé sans espace.** C'est la forme `DDD,MM.mmk` de la spec XMP (Adobe XMP Part 2, type `GPSCoordinate`). **XMP n'a pas de `GPSLatitudeRef`/`GPSLongitudeRef` séparés** : le signe est porté par la lettre finale.

**Fragment XML exact, paquet minimal pour une position GPS :**

```xml
<?xpacket begin='' id='W5M0MpCehiHzreSzNTczkc9d'?>
<x:xmpmeta xmlns:x='adobe:ns:meta/'>
<rdf:RDF xmlns:rdf='http://www.w3.org/1999/02/22-rdf-syntax-ns#'>
 <rdf:Description rdf:about=''
  xmlns:exif='http://ns.adobe.com/exif/1.0/'
  exif:GPSVersionID='2.3.0.0'
  exif:GPSLatitude='43,32.28000000N'
  exif:GPSLongitude='5,2.94000000E'
  exif:GPSAltitude='120/1'
  exif:GPSAltitudeRef='0'/>
</rdf:RDF>
</x:xmpmeta>
<?xpacket end='w'?>
```
*(le `begin='…'` contient le BOM UTF-8 `EF BB BF`, invisible ci-dessus)*

**Taille — MESURE** (je l'ai construit et compté en Python) :
- Paquet XMP seul, UTF-8 : **434 octets**
- Sans l'enveloppe `<?xpacket…?>` (autorisé en PNG/WebP) : **361 octets**
- Payload APP1 JPEG (= 29 octets de signature `http://ns.adobe.com/xap/1.0/\0` + paquet) : **463 octets**
- Segment APP1 complet (marqueur `FFE1` + longueur 2 octets) : **467 octets**

ExifTool ajoute par défaut `$numPadLines = 24` lignes de blancs (~2 Ko) pour permettre la réécriture en place ; **inutile ici**, on réécrit le fichier entier.

**Note `exif:GPSAltitude` :** type `rational` (source XMP.pm), donc `'120/1'`, pas `'120'`. `exif:GPSAltitudeRef` est un `integer` : `0` = Above Sea Level, `1` = Below Sea Level.

**Emplacements par conteneur (tous vérifiés) :**
- **JPEG** : segment APP1 (`FFE1`), payload préfixé de `http://ns.adobe.com/xap/1.0/\0`. Au-delà de 64 Ko → XMP étendu avec `http://ns.adobe.com/xmp/extension/\0` (hors sujet ici, on est à 434 octets).
- **PNG** : chunk `iTXt`, mot-clé `XML:com.adobe.xmp`, compression flag 0. **NON VÉRIFIÉ dans le texte de la spec PNG 3ᵉ édition** — je n'ai pas pu ouvrir la section correspondante (le document W3C revient tronqué). À confirmer sur https://www.w3.org/TR/png-3/ §11.3.4.
- **WebP** : chunk FourCC `'XMP '` (**avec espace de fin, 0x20**) — vérifié sur la spec Google RIFF, + bit 5 (MSB 0) du VP8X à 1.
- **ISOBMFF (HEIC/AVIF)** : box `uuid` avec l'UUID `BE7ACFCB-97A9-42E8-9C71-999491E3AFAC`. **NON VÉRIFIÉ** — cet UUID vient de ma mémoire, pas d'une source consultée dans cette session. À confirmer dans ISO/IEC 14496-12 ou dans `lib/Image/ExifTool/QuickTime.pm`.

## 6. Question 5 — IPTC : ⚠️ CORRECTION À REMONTER AU DEMANDEUR

**L'IPTC IIM ne porte AUCUNE coordonnée. Il n'y a ni latitude ni longitude dans le standard IIM.**

Confirmé sur la spec **IPTC Photo Metadata Standard 2025.1** (iptc.org). Les DataSets IIM liés au lieu sont **tous textuels** :

| IIM DataSet | Nom | Type |
|---|---|---|
| 2:90 | City | texte |
| 2:92 | Sublocation | texte |
| 2:95 | Province/State | texte |
| 2:100 | Country/Primary Location Code | texte |
| 2:101 | Country/Primary Location Name | texte |

Ce sont des **toponymes**, qui décrivent le *contenu* de l'image, pas la position du boîtier. Aucun n'accepte de valeur numérique de coordonnée.

**Où l'IPTC porte-t-il des coordonnées ? Uniquement en XMP, via `Iptc4xmpExt:LocationCreated` — et même là, il emprunte le namespace `exif`.**

Preuve directe, source ExifTool `lib/Image/ExifTool/XMP2.pl`, ligne 332 et suivantes (**verbatim**) :

```perl
my %sLocationDetails = (
    STRUCT_NAME => 'LocationDetails',
    NAMESPACE   => 'Iptc4xmpExt',
    GROUPS      => { 2 => 'Location' },
    NOTES => 'Note that the GPS elements of this structure are in the "exif" namespace.',
    Identifier    => { List => 'Bag', Namespace => 'xmp' },
    City          => { },
    CountryCode   => { },
    CountryName   => { },
    ProvinceState => { },
    Sublocation   => { },
    WorldRegion   => { },
    LocationId    => { List => 'Bag' },
    LocationName  => { Writable => 'lang-alt' },
    GPSLatitude   => { Namespace => 'exif', %latConv },   # <-- namespace exif
    GPSLongitude  => { Namespace => 'exif', %longConv },  # <-- namespace exif
    GPSAltitude   => { Namespace => 'exif', Writable => 'rational' },
    GPSAltitudeRef=> { Namespace => 'exif', Writable => 'integer' },
);
```

et lignes 603/608 :
```perl
LocationCreated => { Struct => \%sLocationDetails, ... },
LocationShown   => { Struct => \%sLocationDetails, ... },
```

`LocationCreated` = « où était l'appareil ». `LocationShown` = « ce qu'on voit sur la photo ». La spec IPTC 2025.1 précise pour `LocationCreated` : *cardinalité 0..1*, avec la note *« IPTC is aware of limiting the count to one… therefore we recommend that at the user interface… only a single location should be supported. »*

**Conséquences pour Geotagor :**
1. **Rayer « écriture IPTC » du périmètre.** Il n'y a rien à écrire : l'IIM n'a pas de coordonnées et l'IPTC Extension délègue à `exif:`.
2. La **lecture** IPTC reste utile pour *afficher* le lieu textuel (« Aix-en-Provence, France ») à côté des coordonnées — c'est une fonctionnalité de confort, pas de géolocalisation.
3. Le triplet réel à écrire est : **EXIF GPS IFD** (canonique) + **XMP `exif:GPS*`** (interopérable) + optionnellement **`Iptc4xmpExt:LocationCreated`** avec ses champs GPS *dans le namespace exif*. Trois écritures, deux formats de valeur (rationnels DMS pour l'EXIF, chaîne `DDD,MM.mmk` pour le XMP).

**Sur `heic2any` précisément.** Il déclare `"license": "MIT"` dans son `package.json` — **mais c'est faux en pratique**. J'ai grepé son bundle minifié : il contient **3 occurrences de `libheif` et 4 de `LIBHEIF`**. C'est un build Emscripten de libheif embarqué. Or le README de `strukturag/libheif` dit (verbatim) :

> « The libheif is distributed under the terms of the GNU Lesser General Public License. The sample applications are distributed under the terms of the MIT License. »

Le MIT de heic2any ne couvre donc que la *fine couche wrapper* de l'auteur ; le wasm embarqué reste **LGPL**. (Le README libheif ne précise pas le numéro de version LGPL ; npm déclare `LGPL-3.0` pour `libheif-js`. Il ajoute aussi : *« note that x265 is GPL »* — encodage seulement, sans objet ici.)

**Note LGPL + wasm :** la LGPL exige que l'utilisateur puisse relier une version modifiée de la bibliothèque. Un `.wasm` livré séparément et chargé dynamiquement est *défendable*, un `.wasm` inliné en base64 dans un bundle ne l'est pas. Ce n'est pas une question tranchable ici — mais la contrainte du projet dit **MIT/BSD/Apache-2.0 uniquement**, donc **toutes ces options sont hors périmètre**, débat LGPL/wasm compris.

**Et de toute façon, le budget explose.** `heic2any` = **337 596 octets gzip** pour le seul décodeur, contre un budget WASM de **400 Ko compressé** — il le consomme à 84 % pour une fonction d'agrément (l'aperçu), pas pour la fonction cœur (lire/écrire le GPS).

**→ Recommandation : renoncer au décodage HEIC.**
1. `exifr` lit le GPS des HEIC **sans décoder l'image** (il ne fait que parcourir les boxes ISOBMFF). **La fonction cœur marche déjà sur HEIC, sans wasm.**
2. Pour l'aperçu : tenter `createImageBitmap(file)` — ça réussit sur Safari 17+, échoue ailleurs. En cas d'échec, afficher une **vignette de substitution + la carte**, avec un message explicite (« aperçu HEIC non disponible dans ce navigateur ; les coordonnées sont bien lues »). Coût : 0 octet.
3. Piste alternative **NON VÉRIFIÉE, à instruire** : beaucoup de HEIC iPhone embarquent une **vignette JPEG** dans un item `thmb`/`Exif` de l'ISOBMFF. L'extraire donnerait un aperçu gratuit, en JS pur, sans décodeur HEVC. À valider sur des fichiers iPhone réels — ce serait la meilleure solution si ça tient.

## CE QU'IL FAUDRA ÉCRIRE À LA MAIN

| # | Chantier | Difficulté | Volume estimé | Détail |
|---|---|---|---|---|
| **1** | **PNG — chunk `eXIf`** | 🟢 **Facile** | ~120 l. | Le plus simple des quatre. **Le contenu du chunk est le blob TIFF nu, SANS le préfixe `Exif\0\0`** — vérifié sur la spec des extensions PNG (pngext-1.5.0), verbatim : *« The data segment of the eXIf chunk contains an Exif profile in the format specified in "4.7.2 Interoperability Structure of APP1 in Compressed Data" of [CIPA DC-008-2016] except that the JPEG APP1 marker, length, and the "Exif ID code"… are not included. »* Doit commencer par `II`+42 ou `MM`+42. Règles : *« Only one eXIf chunk is allowed in a PNG datastream »*, *« may appear anywhere between the IHDR and IEND chunks except between IDAT chunks »*. `png-chunks-extract` + `png-chunks-encode` (MIT, ~60 l. chacun, vendorables) font le découpage et le **CRC32**. Reste à écrire : insertion/remplacement du chunk + le chunk `iTXt` pour le XMP. |
| **2** | **WebP — VP8X + chunks `EXIF` / `XMP `** | 🟡 **Moyenne** | ~250 l. | Spec Google RIFF vérifiée. Deux cas : (a) le fichier est déjà *extended* (`VP8X` présent) → poser le **bit 4** (EXIF) et/ou le **bit 5** (XMP) de l'octet de flags (numérotation MSB 0), puis ajouter/remplacer le chunk `'EXIF'` ou `'XMP '` (**FourCC avec espace de fin**) ; (b) le fichier est *simple* → **il faut fabriquer le VP8X**, ce qui impose de connaître canvas width/height (24 bits chacun, moins un) et donc de parser l'en-tête `VP8 ` (lossy) ou `VP8L` (lossless). Point verbatim de la spec : les fichiers simples ne peuvent **pas** porter d'EXIF. Plus le padding RIFF à parité et la mise à jour de la taille globale. |
| **3** | **TIFF — IFD in-place** | 🔴 **Difficile** | ~500 l. | Le seul conteneur où l'EXIF *est* la structure du fichier. Insérer un GPS IFD déplace tout ce qui suit → **il faut recalculer chaque offset** (`StripOffsets`, `TileOffsets`, `JPEGInterchangeFormat`, sous-IFD, MakerNotes). Big-endian *et* little-endian obligatoires en lecture ET en écriture (contrairement au JPEG où on peut normaliser). BigTIFF hors périmètre. `utif2` (MIT) ne sert pas : il décode les pixels. **C'est le chantier le plus coûteux au ratio effort/usage** — les TIFF sont rares chez le grand public. |
| **4** | **ISOBMFF (HEIC/AVIF) — item `Exif` + box `uuid` XMP** | 🔴🔴 **Très difficile** | ~800 l. | Il faut parser `meta` → `hdlr`, `iinf`/`infe` (trouver l'item de type `Exif`), `iloc` (offsets/longueurs), `iref`, `pitm`. Écrire = modifier la charge EXIF, **puis recalculer toutes les entrées `iloc`** (qui peuvent être relatives au fichier, à l'`idat`, ou à un item), **puis** décaler `mdat`. Si aucun item `Exif` n'existe, il faut en **créer** un : nouvelle `infe`, nouvelle entrée `iloc`, nouvelle `iref` vers l'item primaire. `codem-isoboxer` parse mais **ne sérialise pas**. Aucune brique réutilisable. |
| **5** | **Sérialiseur XMP** | 🟢 **Facile** | ~150 l. | Voir §5. Construction de chaîne + `TextEncoder`. Le vrai travail est la **conversion de format** : décimal → `"%d,%.8f" + ref` (minutes décimales, 8 décimales). Attention à l'échappement XML et au BOM du `xpacket begin`. Mutualisé entre les 4 conteneurs. |
| **6** | **Correctifs / durcissement piexifjs** | 🟡 **Moyenne** | ~200 l. | Conversion `Uint8Array` ⇄ binary string sans exploser la pile (`String.fromCharCode.apply` casse au-delà de ~64 K args → traiter par blocs). Suppression GPS **sélective** (retirer le GPS IFD + le tag 0x8825 sans toucher au reste, ≠ `remove()`). Garde-fou sur les 64 Ko d'APP1. Réordonnancement APP0/APP1. Détection MPF → refus explicite plutôt que corruption silencieuse. |
| **7** | **Harnais de test sur fichiers réels** | 🟡 **Moyenne** | — | **Non négociable.** Corpus minimal : iPhone HEIC + JPEG (dont Portrait/MPF), Android JPEG, Canon (little-endian + MakerNotes), Nikon, Sony, PNG avec/sans eXIf, WebP simple + extended, TIFF LE + BE, fichiers sans EXIF, fichiers à EXIF corrompu. Oracle : comparer à `exiftool` en CI. |

**Total estimé (ESTIME, calcul explicite) :** 120 + 250 + 500 + 800 + 150 + 200 = **~2 000 lignes de manipulation binaire**, hors tests. À ~15–25 lignes utiles/jour sur du parsing binaire à spec (rythme réaliste quand chaque ligne doit être validée contre un fichier réel), cela fait **8 à 14 semaines-homme**. Sans ISOBMFF et sans TIFF : ~720 lignes → **3 à 5 semaines**.

## VERDICT — Faisabilité de la voie JS seule si le Rust échoue

**Verdict : la voie JS seule est VIABLE pour un périmètre réduit à JPEG + PNG (+ WebP), et NON VIABLE pour un périmètre incluant TIFF et HEIC/AVIF en écriture.**

### Ce qui marche, aujourd'hui, avec des briques existantes

| Fonction | Solution | Coût gzip (MESURE) |
|---|---|---|
| **Lire** GPS de JPEG, PNG, TIFF, **HEIC, AVIF** | `exifr/dist/lite.esm.mjs` | **14 766 o** |
| **Écrire/supprimer** GPS en **JPEG** | `piexif-ts@2.1.0` | **12 374 o** |
| **Écrire** XMP GPS (tous conteneurs) | à écrire, ~150 l. | ~1 500 o |
| **Écrire** eXIf/iTXt en **PNG** | `png-chunks-*` vendorés + ~120 l. | ~2 500 o |
| Export ZIP en lot | `client-zip@2.5.0` | **2 676 o** |
| Carte | `leaflet@1.9.4` + CSS | **45 883 o** |
| PWA | `workbox-window@7.4.1` | **2 380 o** |
| **Total noyau JS** | | **~82 Ko gzip** |

**~82 Ko gzip sur un budget de 150 Ko** → il reste **~68 Ko** pour l'UI, les îlots Astro et la recherche de communes. **Le budget tient, et confortablement — à condition d'utiliser Leaflet et non MapLibre.**

### Ce qui ne marche pas

- **HEIC/AVIF en écriture : hors de portée en JS raisonnable.** Or c'est le format par défaut de tous les iPhone depuis iOS 11 — c'est-à-dire **le cas d'usage numéro un** d'un outil grand public de géolocalisation de photos. Le repli JS lit le GPS des HEIC mais **ne peut ni le modifier ni l'effacer**. Pour un outil dont la promesse est « voir, **modifier** et **supprimer** la position », c'est une amputation de la promesse, pas un détail.
- **WebP en lecture : trou complet.** `exifr` ne supporte pas WebP (issue #129 ouverte depuis décembre 2024). Il faudrait écrire **aussi le lecteur** WebP, pas seulement l'écrivain.
- **TIFF en écriture : ~500 lignes pour un format que presque personne n'apporte.** À sacrifier sans regret.
- **Aperçu HEIC hors Safari : impossible** dans les contraintes de licence (toutes les libs sont LGPL-encombrées) et de budget (337 Ko gzip pour heic2any).

### Le point de fragilité stratégique

**Les deux briques du cœur sont non maintenues.** `exifr` : dernier commit **août 2021**, 53 issues ouvertes. `piexifjs` : dernier commit **juin 2019**, v2 morte depuis novembre 2019. Ensemble, elles représentent **27 Ko gzip et 100 % de la fonction cœur**. Ce n'est pas rédhibitoire — ce sont des parseurs de formats gelés, le code correct reste correct — mais cela signifie qu'**aucun bug trouvé ne sera corrigé en amont**. Il faut budgéter le fork et l'appropriation du code, pas seulement l'intégration. `piexif-ts@2.1.0` (MIT, 2024) est le meilleur point de départ pour ce fork.

### Recommandation

1. **Le spike Rust/WASM garde toute sa valeur, et c'est HEIC/AVIF + TIFF qui le justifient** — pas JPEG. Sur JPEG seul, la voie JS est meilleure (12 Ko gzip contre plusieurs centaines de Ko de wasm). **La question à poser au spike R1 n'est donc pas « Rust ou JS ? » mais « `little_exif` sait-il écrire dans un ISOBMFF ? »** Si non, le Rust n'apporte rien de décisif sur le point qui compte, et la voie JS devient le choix par défaut.
2. **Architecture recommandée : hybride, pas exclusive.** JS pour JPEG/PNG (chargé toujours, ~27 Ko gzip) ; WASM chargé en *lazy* uniquement à l'ouverture d'un HEIC/AVIF/TIFF. C'est exactement ce que permet le budget WASM de 400 Ko « chargé en lazy » déjà prévu dans les contraintes.
3. **Trois corrections à acter dans le cahier des charges :**
   - **Retirer « écriture IPTC »** — l'IIM n'a pas de coordonnées (§6).
   - **Remplacer MapLibre par Leaflet** — 273 Ko vs 42 Ko gzip, le budget de 150 Ko l'impose.
   - **Amender l'allowlist de licences** pour y admettre explicitement **OFL-1.1** (polices) et **ISC** (équivalent MIT), ou renoncer aux Fontsource.
4. **Corriger la pile envisagée : `@fontsource-variable/dm-mono` n'existe pas** → utiliser `@fontsource/dm-mono@5.3.0` (statique).
5. **Lever le risque `@vite-pwa/astro` avant de figer la pile** : peerDep plafonnée à Astro 5, Astro est en 7.1.3, aucune version plus récente de l'intégration. Tester l'installation réelle ou prévoir une intégration Workbox manuelle.
