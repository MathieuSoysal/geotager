## 2. Écriture du GPS IFD — QUESTION BLOQUANTE : **OUI, SUPPORTÉ**

**Source : `https://raw.githubusercontent.com/TechnikTobi/little_exif/main/src/exif_tag/mod.rs`, lignes 500-536 et 598.**

La macro `build_tag_enum!` a pour colonnes (lignes 26-34) :
```
( $tag:ident, $hex_value:expr, $format_enum:ident, $component_number:expr, $writable:expr, $group:ident )
```

Extrait littéral de la table (colonne 5 = writable, colonne 6 = groupe) :
```
(GPSVersionID,     0x0000, INT8U,       Some::<u32>(4),  true, GPS),
(GPSLatitudeRef,   0x0001, STRING,      Some::<u32>(2),  true, GPS),
(GPSLatitude,      0x0002, RATIONAL64U, Some::<u32>(3),  true, GPS),
(GPSLongitudeRef,  0x0003, STRING,      Some::<u32>(2),  true, GPS),
(GPSLongitude,     0x0004, RATIONAL64U, Some::<u32>(3),  true, GPS),
(GPSAltitudeRef,   0x0005, INT8U,       Some::<u32>(1),  true, GPS),
(GPSAltitude,      0x0006, RATIONAL64U, Some::<u32>(1),  true, GPS),
(GPSTimeStamp,     0x0007, RATIONAL64U, Some::<u32>(3),  true, GPS),
(GPSDateStamp,     0x001d, STRING,      Some::<u32>(11), true, GPS),
```
**Les 8 tags demandés sont tous présents, tous `writable=true`, tous groupe `GPS`.** La table couvre en réalité 0x0000→0x001f (32 tags GPS).

Mécanique d'affectation à l'IFD GPS, vérifiée :
- `pub enum ExifTagGroup { GENERIC, EXIF, INTEROP, GPS }` — `src/ifd/mod.rs` ligne ~42-50.
- `pub fn get_group(&self) -> ExifTagGroup` généré par macro : `ExifTag::$tag(_) => ExifTagGroup::$group` (`exif_tag/mod.rs` l. 291-301).
- `pub fn is_writable(&self) -> bool` : `ExifTag::$tag(_) => $writable` (l. 223-237).
- Tag pointeur : `(GPSInfo, 0x8825, INT32U, Some::<u32>(1), true, GENERIC)` (l. 598) + `ExifTag::GPSInfo(_) => TagType::IFD_OFFSET(ExifTagGroup::GPS)` (l. 717). C'est le lien IFD0 → GPS IFD.
- API publique : `Metadata::set_tag(&mut self, input_tag: ExifTag)`, `create_ifd(&mut self, ifd_type: ExifTagGroup, generic_ifd_nr: u32)`, `get_ifd(&self, group: ExifTagGroup, generic_ifd_nr: u32)`, `remove_tag_by_hex_group(&mut self, tag_hex: u16, tag_group: ExifTagGroup)` (docs.rs `struct.Metadata.html`).
- `encode()` construit et chaîne les IFDs et réécrit les offsets (`metadata/mod.rs`), avec `sort_tags()` respectant TIFF 6.0 (« The entries in an IFD must be sorted in ascending order by Tag », commentaire cité dans `ifd/mod.rs`).

Statut : **DOCUMENTÉ + code source lu**. Rien n'est encore **MESURÉ** à l'exécution.

⚠️ Attention formats : `GPSAltitudeRef` est `INT8U` et `GPSTimeStamp`/`GPSAltitude` sont `RATIONAL64U`. Les issues fermées #38 et #74 (« get illegal format for known tag! Tag: GPSAltitudeRef([]) Expected: INT8U Got: INT16U ») montrent que des fichiers réels violent la spec sur ce tag précis. **À couvrir explicitement dans le spike.**

## 6. XMP et IPTC — **EXIF SEULEMENT**

`src/lib.rs` déclare bien `mod xmp;` (privé), mais `src/xmp.rs` (© 2025) ne contient qu'**une seule fonction, `pub(crate)`** :

```rust
pub(crate) fn remove_exif_from_xmp(data: &[u8]) -> Result<Vec<u8>, Box<dyn std::error::Error>>
```

Son doc-comment : *« Some images also contain XMP metadata, which in turn may include EXIF data that is simply a duplicate from e.g. the eXIf chunk in a PNG. This function takes in the raw XMP information and removes EXIF attributes, while maintaining other XMP information... »*

C'est un **utilitaire interne de dé-duplication**, pas une API d'écriture XMP. Non exposé publiquement.

- **XMP : lecture/filtrage interne uniquement, aucune écriture exposée.** Issues ouvertes #95 « How to handle EXIF+XMP? » et #37 « Feature request: XMP -> EXIF conversion » confirment que c'est un manque assumé et non résolu.
- **IPTC : absent.** Seul `clear_app13_segment` (JPEG APP13/Photoshop) permet de *supprimer* le bloc qui contient l'IPTC — pas de le lire ni l'écrire. Issue ouverte #42 « Feature Request: Photoshop Tags ».

**Recommandation franche : il faudra écrire le XMP à la main.** C'est en réalité l'option la plus saine pour Geotagor :
- Le XMP géo se réduit à `exif:GPSLatitude`, `exif:GPSLongitude`, `exif:GPSAltitude` en RDF/XML — quelques dizaines de lignes de sérialisation, pas de crate nécessaire.
- **Surtout, pour un outil de suppression de position GPS, il est impératif de purger AUSSI le XMP** : effacer le GPS IFD en laissant `exif:GPSLatitude` dans le XMP est une fuite de vie privée. `remove_exif_from_xmp` étant `pub(crate)`, **cette purge n'est pas accessible depuis l'extérieur du crate** → à réimplémenter côté projet, ou à obtenir par PR upstream.
- Aucun crate Rust XMP/IPTC crédible identifié en écriture. `rexiv2` couvrirait XMP+IPTC mais est **GPL-3.0-or-later** (viole la contrainte de licence) **et** lie `gexiv2`/Exiv2 en C/C++ (inutilisable en `wasm32-unknown-unknown`). **NON VÉRIFIÉ** : je n'ai pas fait de recherche exhaustive du registre crates.io pour « xmp » / « iptc ».

## 7. WebP lossy simple → VP8X sans réencodage : **NON, PAS IMPLÉMENTÉ**

**Preuve littérale**, `src/webp/vec.rs`, fonction `convert_to_extended_format` :

```rust
let (width, height) = match first_chunk.descriptor().header().as_str()
{
    "VP8 "
        => {log::debug!("VP8 !"); io_error!(Other, "Conversion from Simple File Format with 'VP8' chunk to Extended File Format not yet implemented!") },
    "VP8L"
        => get_dimension_info_from_vp8l_chunk(first_chunk.payload()),
    _
        => io_error!(Other, format!("Expected either 'VP8 ' or 'VP8L' chunk for conversion but got {:?}!", first_chunk.descriptor().header().as_str()))
}?;
```

- **VP8L (lossless) → VP8X : implémenté.** Le VP8X est construit à la main (fourCC `VP8X`, taille 0x0A, flags, width-1/height-1 sur 24 bits chacun), inséré à l'offset 12 via `insert_multiple_at`, puis `update_file_size_information(cursor, 18)` corrige la taille RIFF. **Aucun réencodage de pixels** — c'est bien de la chirurgie de conteneur.
- **VP8 (lossy simple) → VP8X : erreur explicite, non implémenté.** Cohérent avec le README « WebP (only lossless and extended) ».

**Nuance intéressante et exploitable** : la brique manquante *existe déjà*. `src/webp/mod.rs` contient `get_dimension_info_from_vp8_chunk(payload: &[u8]) -> Result<(u32, u32), std::io::Error>`, qui valide le magic `[0x9d, 0x01, 0x2a]` et extrait width/height 14 bits du header de frame VP8 (RFC 6386 §9.1). Elle est référencée dans `src/webp/file.rs` mais **pas** dans `src/webp/vec.rs` (0 occurrence) — donc pas câblée dans le chemin mémoire.

→ **Le gap est petit et bien cerné** : brancher `"VP8 " => get_dimension_info_from_vp8_chunk(...)` dans `convert_to_extended_format`. Candidat idéal à une PR upstream, ou à un patch/fork temporaire. Attention à l'invariant `assert!(old_file_size % 2 == 0)` (padding RIFF) présent dans `update_file_size_information` — un `assert!` = panic en wasm.

⚠️ Lecture WebP : `check_exif_in_file` **exige** que le premier chunk soit `VP8X`, sinon erreur. Un WebP lossy simple sans EXIF déclenchera donc une erreur explicite, pas un crash — comportement acceptable si l'UI le gère.

**Par thème demandé :**

- **GPS** : #38 « SubIFD GPS Decode Error: Unexpected format for GPSAltitudeRef » (fermée, oct. 2024), #74 « get illegal format for known tag! Tag: GPSAltitudeRef([]) Expected: INT8U Got: INT16U » (fermée, nov. 2025), #43 « GPS infos not found » (fermée), #49 « unable to extract GPSLatitude / GPSLongitude works » (fermée). **Toutes fermées**, mais le motif est récurrent : `GPSAltitudeRef` mal typé par des encodeurs réels. Historique rassurant (le mainteneur corrige) mais la classe de bug est vivante.
- **Big-endian** : `Endian::{Little, Big}` géré explicitement dans `Metadata::decode` (validation `[0x49,0x49]`/`[0x4d,0x4d]` + magic number `0x2a00`/`0x002a`). **Aucune issue ouverte trouvée** sur le big-endian. Mais `Metadata::new()` force `Endian::Little` — **une photo big-endian (Canon, Nikon) risque d'être réécrite en little-endian**. Conséquence fonctionnellement neutre mais qui **modifie plus d'octets que nécessaire** : à vérifier au spike si l'endianness d'origine est préservée en round-trip.
- **JPEG MPF (Multi-Picture Format)** : **AUCUN support.** 0 occurrence de `MPF`/`multi-picture`/`APP2` dans `src/jpg.rs` (508 lignes, vérifié). Les JPEG multi-images (portraits iPhone, Samsung, GoPro) verront leur segment APP2/MPF conservé tel quel mais **ses offsets absolus deviendront invalides** si la taille de l'APP1 change. **Risque réel de corruption silencieuse** sur photos de smartphones récents. À tester impérativement.
- **Préservation des segments non modifiés** : le design est encourageant. `clear_segment(file_buffer, segment_marker, prefix)` parcourt les marqueurs et ne supprime que le segment ciblé **avec vérification du préfixe** (`EXIF_HEADER` pour l'APP1) via le drapeau `do_not_delete_segment_override` — un APP1 XMP (préfixe `http://ns.adobe.com/xap/1.0/`) ne sera donc pas détruit par erreur. **DOCUMENTÉ par le code, NON MESURÉ.** Contre-indication : issue ouverte #93 signale des erreurs en round-trip.

**Critères d'arrêt (à fixer avant de lancer le spike) :**
- Si `.wasm` optimisé + brotli **> 400 Ko** → NO-GO Rust, sauf si `twiggy` montre que brotli/JXL sont retirables par fork ou PR upstream.
- Si un panic est atteignable sur le corpus adversarial sans possibilité de le convertir en `Err` → NO-GO (ou isolation stricte + recréation du module wasm après crash).

- Si le repli JS (exifr + piexifjs) tient dans un budget nettement plus petit avec une couverture équivalente → **préférer JS**, la contrainte 150 Ko JS / 400 Ko WASM est serrée.
