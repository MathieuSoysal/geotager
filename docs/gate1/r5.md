# R5 — Chaîne de build et hébergement (GEOTAGOR)

## 0. Résumé exécutif

**Recommandation : Astro 7, pas Vite nu.** Mais avec un renversement important par rapport à la pile envisagée : **ne pas utiliser `client:idle` ni d'îlot hydraté**. Le mécanisme documenté d'Astro pour du JS vanilla est `<script>` + custom elements, dont le coût de runtime Astro est **0 octet** — contre 2093 B gzip minimum (mesuré) pour la voie `client:idle`, plus le framework UI lui-même.

Astro 7 (blog officiel, [astro.build/blog/astro-7](https://astro.build/blog/astro-7/), DOCUMENTÉ) : compilateur `.astro` réécrit **en Rust** (remplace le Go), pipeline Markdown/MDX Rust (« Sätteri »), **Vite 8 avec Rolldown**, builds 15–61 % plus rapides. ### `output: 'static'` (DOCUMENTÉ, [configuration-reference](https://docs.astro.build/en/reference/configuration-reference/))

Valeurs `'static' | 'server'`, **défaut `'static'`** — rien à configurer. Options utiles vérifiées : `build.inlineStylesheets` (`'auto'` par défaut), `build.assets` (`'_astro'`), `compressHTML` (défaut **`'jsx'`** depuis v7 — changement de comportement à noter), `site` (requis pour sitemap + canoniques).

### La question centrale : îlot SANS framework UI ?

**Réponse : non, pas un « îlot » au sens `client:*` — et c'est une bonne nouvelle.**

La doc des directives ([directives-reference](https://docs.astro.build/en/reference/directives-reference/)) est explicite (DOCUMENTÉ) :

> « A client directive can only be used on a UI framework component that is directly imported into a `.astro` component. »

Donc `client:idle` **exige** React/Preact/Svelte/Vue + son intégration. Impossible en JS vanilla.

**Coût réel de la voie `client:idle` (MESURÉ)** — fichiers tirés de `unpkg.com/astro@7.1.3`, compressés localement avec `node:zlib` :

| Fichier | brut | gzip -9 | brotli q11 |
|---|---|---|---|
| `dist/runtime/server/astro-island.prebuilt.js` | 4 493 B | 1 824 B | 1 578 B |
| `dist/runtime/client/idle.js` | 501 B | 269 B | 235 B |
| **Sous-total runtime Astro** | **4 994 B** | **2 093 B** | **1 813 B** |
| (`load.js` 165 B, `visible.js` 633 B, `media.js` 390 B — bruts, pour référence) | | | |

`astro-island.prebuilt.js` est un **template string** injecté inline dans le HTML : c'est le custom element `<astro-island>` qui désérialise les props et appelle `this.hydrator`, lequel provient du renderer client du framework. **Ces ~2 Ko gzip ne sont que le ticket d'entrée** ; il faut y ajouter le renderer d'intégration + le framework (Preact ≈ 4–5 Ko gzip, React ≈ 45 Ko gzip — **NON VÉRIFIÉ, je ne les ai pas mesurés**).

Le contenu de `idle.js` (MESURÉ, lu intégralement) est trivial — 17 lignes qui appellent `requestIdleCallback` avec repli `setTimeout(cb, timeout || 200)`. Aucune valeur ajoutée qu'on ne réécrirait pas en 6 lignes.

### Le mécanisme recommandé : `<script>` + custom elements

La doc [client-side-scripts](https://docs.astro.build/en/guides/client-side-scripts/) (DOCUMENTÉ) décrit exactement la voie vanilla :

- « All scripts are TypeScript by default »
- « Processed scripts become `type="module"` automatically »
- Bundling des imports locaux et npm, **déduplication** (« the script will only be included once » même si le composant est utilisé N fois)
- Inlining automatique des petits scripts pour économiser une requête
- `is:inline` pour désactiver tout traitement

Et pour l'interactivité : « You can create your own HTML elements with custom behavior using the Web Components standard » — avec un exemple `<astro-heart>` montrant « interactive components without needing a UI framework library », `connectedCallback()` gérant les instances multiples.

La doc [concepts/islands](https://docs.astro.build/en/concepts/islands/) confirme le socle : « Astro components are the building blocks of your page template. **They render to static HTML with no client-side runtime.** »

**Conséquence pour le budget 150 Ko gzip : la voie vanilla consomme 0 octet de runtime Astro.** Tout le budget va au code métier (EXIF, carte, recherche). C'est le choix évident ici — d'autant que l'UI de GEOTAGOR (drop-zone, tableau EXIF, carte, champs lat/lon) n'a aucun besoin d'un VDOM.

Pour reproduire `client:idle` en vanilla, 6 lignes suffisent :
```js
const boot = () => import('./exif-panel.js').then(m => m.mount(el));
'requestIdleCallback' in window ? requestIdleCallback(boot, {timeout: 2000}) : setTimeout(boot, 200);
```

## 2. Astro vs Vite + HTML multipage

Ce qu'Astro apporte gratuitement, **vérifié package par package** (MESURÉ, npm) :

| Paquet | Version | Licence | Publié | Apport |
|---|---|---|---|---|
| `@astrojs/sitemap` | 3.7.3 | MIT | 2026-05-26 | `sitemap-index.xml` + `sitemap-0.xml`, crawl des routes statiques y compris dynamiques, options `filter`, `customPages`, `i18n`, `changefreq`, `lastmod`, `serialize`. **Exige `site`.** ⚠️ N'ajoute **pas** le lien dans `robots.txt` — à faire à la main via `src/pages/robots.txt.ts` |
| `@astrojs/check` | 0.9.9 | MIT | 2026-04-28 | Typecheck `.astro` (peer `typescript ^5 \|\| ^6`) |
| `@astrojs/mdx` | 7.0.3 | MIT | 2026-07-13 | peer `astro: ^7.0.0` — écosystème bien à jour sur v7 |

Intégrés au cœur, sans paquet (DOCUMENTÉ) :
- **Content collections / Content Layer** : Markdown/MDX typé avec schémas Zod, pipeline Rust en v7.
- **Images** ([guides/images](https://docs.astro.build/en/guides/images/)) : `<Image />` / `<Picture />`, service **Sharp** par défaut, transformation **au build** pour les pages prérendues, sans adaptateur. Sortie AVIF/WebP avec repli. Et surtout : « The `<Image />` component optimizes for CLS by automatically setting the correct `width` and `height` » — **directement acquis sur le budget CLS ≤ 0,1**.
- **API Fonts** (voir §5).
- **API CSP** (stable depuis Astro 6) — utile pour verrouiller le zéro-tiers.

### Chiffrage du delta (ESTIMÉ — hypothèse ~1 j = 7 h de dev)

Sur 4 pages statiques, le travail à réécrire soi-même en Vite nu :

| Tâche | Vite nu | Astro |
|---|---|---|
| Routage multipage + layouts partagés | `rollupOptions.input` manuel + duplication du `<head>`, ou moteur de templates ajouté | natif |
| Rendu Markdown (4 pages + contenu SEO) | intégrer markdown-it/unified, frontmatter, coquille HTML | collections natives |
| Sitemap | script maison | 1 ligne |
| Images responsives + width/height (CLS) | pipeline sharp maison | `<Image />` |
| Polices auto-hébergées + preload + fallback metrics | manuel (voir §5) | API Fonts |
| Typecheck des templates | inexistant | `@astrojs/check` |

**Estimation : 3 à 5 jours de mise en place initiale + une dette d'entretien permanente**, contre ~0,5 j en Astro. Le calcul : 6 chantiers × 0,5–1 j chacun. Et la dette est récurrente — le pipeline images/CLS maison devra être maintenu à chaque évolution.

**Le seul argument pour Vite nu** — « Astro pèse dans le bundle » — est **faux ici** : en voie vanilla, Astro n'expédie littéralement aucun runtime. On ne paie qu'au build. **Verdict : Astro 7, sans hésitation.**

## 3. Cloudflare Pages

### Compression (MESURÉ, sur un vrai déploiement Pages)

J'ai sondé `astro-docs.pages.dev` (déploiement Pages réel) :

| `Accept-Encoding` envoyé | `content-encoding` reçu |
|---|---|
| `br, gzip` | **`br`** |
| `gzip` | `gzip` |
| `br` | **`br`** |

→ **Cloudflare négocie Brotli automatiquement. Rien à faire, et les fichiers `.br` précompressés sont inutiles.**

⚠️ Nuance honnête, car j'ai vu l'inverse ailleurs : `astro.build` et `starlight.astro.build` (mêmes en-têtes `server: cloudflare`) m'ont renvoyé **`gzip`**, et `astro.build` avec `Accept-Encoding: br` seul m'a renvoyé **aucune compression**. La compression dépend donc de la configuration de zone (Compression Rules), pas seulement de Pages. **À revérifier sur notre propre domaine après déploiement** — c'est un contrôle à automatiser.

**Servir des `.br` précompressés : NON VÉRIFIÉ.** La page `developers.cloudflare.com/workers/static-assets/compression/` renvoie 404 et la recherche documentaire n'a rien donné de concluant. *Pour vérifier : déployer un `test.js` + `test.js.br` sur un projet Pages jetable et comparer les réponses.* En pratique, la question est sans objet puisque la compression auto fonctionne.

### Limites (DOCUMENTÉ, [pages/platform/limits](https://developers.cloudflare.com/pages/platform/limits/))

| Limite | Valeur |
|---|---|
| Fichiers par site | **20 000 (Free)** / 100 000 (payant) |
| Taille max d'un asset | **25 MiB** |
| Règles `_headers` | **100 max**, **2 000 caractères par ligne** |
| `_redirects` | 2 000 statiques / 100 dynamiques |
| Builds | 500/mois + 1 concurrent (Free), timeout **20 min** |
| Projets par compte | 100 |
| **Taille totale du site** | **NON DOCUMENTÉ** sur cette page |

🚨 **Alerte architecture pour l'index de communes.** Il y a ~35 000 communes en France. **Un fichier par commune dépasse la limite Free de 20 000 fichiers.** Le shard par lettre (26 fichiers) passe très largement — mais si un shard plus fin est envisagé (préfixe 2–3 lettres), il faut compter les fichiers au build et échouer au-delà d'un seuil (voir §7).

### `_headers` (DOCUMENTÉ, [pages/configuration/headers](https://developers.cloudflare.com/pages/configuration/headers/))

Blocs multi-lignes, splat unique `*`, placeholders `:nom`, héritage cumulatif des règles qui matchent. Exemple de cache long tiré de la doc :

```
/static/*
  Cache-Control: public, max-age=31556952, immutable
```

Pour GEOTAGOR (les shards et le WASM étant versionnés par hash de contenu) :

```
/_astro/*
  Cache-Control: public, max-age=31536000, immutable
/index/*
  Cache-Control: public, max-age=31536000, immutable
/*
  Cache-Control: public, max-age=0, must-revalidate, no-transform
  X-Content-Type-Options: nosniff
  Referrer-Policy: no-referrer
```

Le fichier va dans le répertoire de sortie — donc dans `public/_headers` côté Astro. Contrainte notée : « Custom headers defined in the `_headers` file are not applied to responses generated by Pages Functions » (sans objet, on n'en a aucune).

### Zéro cookie, zéro script injecté

**Zéro cookie : MESURÉ et confirmé.** `astro-docs.pages.dev` ne renvoie **aucun `Set-Cookie`**.

⚠️ Mais j'ai mesuré `Set-Cookie: __cf_bm=...` sur `developers.cloudflare.com`, `blog.cloudflare.com` et `astro.pages.dev`. Le cookie `__cf_bm` (Bot Management) apparaît selon la configuration de zone. **À vérifier sur notre domaine** : Bot Fight Mode doit rester désactivé.

**Injection de scripts — trois vecteurs identifiés, tous à neutraliser :**

1. **Cloudflare Web Analytics** ([rum-beacon](https://developers.cloudflare.com/speed/observatory/rum-beacon/), DOCUMENTÉ). En « one-click setup », le beacon JS est « *automatically* injected into pages as the HTML response passes through Cloudflare's edge network ». Deux sous-cas :
   - site proxifié + setup auto → rapporte vers **`/cdn-cgi/rum` sur votre propre domaine** (donc pas de domaine tiers — mais **c'est de la télémétrie**, ce qui viole la contrainte « zéro télémétrie ») ;
   - setup manuel → charge `https://static.cloudflareinsights.com/beacon.min.js` (**domaine tiers**).
   
   **Parade documentée et vérifiable** : la FAQ précise que si `Cache-Control` vaut `public, no-transform`, « Cloudflare proxy will not be able to modify the original payload of the website. Therefore, the Beacon script will not be automatically injected ». → d'où le `no-transform` dans le `_headers` ci-dessus. **Ceinture et bretelles : ne pas activer Web Analytics du tout.**

2. **Email Address Obfuscation** (WAF/Scrape Shield) injecte `email-decode.min.js` (DOCUMENTÉ, [changelog 2026-04-14](https://developers.cloudflare.com/changelog/post/2026-04-14-email-obfuscation-defer/) — le script est désormais `defer`, mais **il est toujours injecté**). → à désactiver dans Scrape Shield.

3. **Rocket Loader** (diffère/réécrit le JS). Statut par défaut **NON VÉRIFIÉ** — *à vérifier dans le dashboard, onglet Speed > Optimization, et à laisser Off.*

**Contrôle final recommandé** : après déploiement, `curl -s https://geotagor.xx/ | grep -ciE 'cdn-cgi|cloudflareinsights|email-decode|rocket'` doit renvoyer 0, et `curl -sI` ne doit contenir aucun `Set-Cookie`. À câbler en test de fumée post-déploiement.

### Note stratégique : Pages ou Workers Static Assets ?

Cloudflare pousse activement **Workers Static Assets** ([guide de migration](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/), DOCUMENTÉ) : « Unlike Pages, Workers has a distinctly broader set of features ». `_headers` et `_redirects` y sont supportés nativement. Je n'ai **pas trouvé de formulation explicite « utilisez Workers pour les nouveaux projets »** (NON VÉRIFIÉ), mais la direction du produit est nette. Pour un site 100 % statique sans Functions, **Pages reste parfaitement adapté et plus simple** ; la migration éventuelle est une réécriture de `wrangler.toml` de ~5 lignes, sans risque de blocage.

- **(b)** **service worker écrit à la main** — c'est mon conseil ici.

### Pourquoi un SW manuel pour GEOTAGOR

Coût runtime de Workbox (MESURÉ) : `workbox-window@7.4.1` (MIT), build `prod.umd.js` = 6 060 B brut / **2 360 B gzip** / 2 105 B brotli ; le build ESM `prod.mjs` fait 3 343 B brut. Ce n'est pas énorme, mais Workbox est conçu pour du routage de cache complexe. GEOTAGOR a **trois classes d'actifs seulement**, toutes immuables et hashées. Un SW manuel de ~60 lignes couvre tout, sans dépendance, sans risque de peer mismatch, et avec un contrôle total sur la mise à jour — qui est ici le vrai sujet.

### Stratégie de cache

| Classe | Stratégie | Motif |
|---|---|---|
| Coquille d'app (HTML, CSS, JS `_astro/*`) | **Precache** à `install` | offline intégral immédiat |
| Module WASM EXIF | **Cache-first**, précaché à `install` *ou* au premier usage | 400 Ko compressés : précacher pénalise la première visite. Recommandation : **lazy + cache-first**, avec précache déclenché après le premier usage réussi |
| Shards d'index de communes | **Cache-first, à la demande** | 26 shards ; ne précacher que ceux réellement demandés, sinon on télécharge tout l'index pour rien |
| Contours de carte | idem shards | idem |

Les trois classes étant hashées par contenu, `Cache-Control: immutable` + cache-first est sûr : un changement de contenu change l'URL.

### Mise à jour du SW sans casser un utilisateur en cours de travail

C'est **le point critique** pour GEOTAGOR : l'utilisateur peut avoir 40 photos chargées en mémoire, non exportées. Un rechargement automatique **détruit son travail**.

La doc vite-pwa ([auto-update](https://vite-pwa-org.netlify.app/guide/auto-update.html), DOCUMENTÉ) est formelle :

> `registerType: 'autoUpdate'` force `workbox.clientsClaim` et `workbox.skipWaiting` à `true` — « The disadvantage of using this behavior is that **the user can lose data** in any browser windows/tabs in which the application is open and is filling in a form. »
>
> « we recommend you to change the behavior to use default `prompt` option to allow the user decide when to update »

**Décision : `prompt`, jamais `autoUpdate`.** Concrètement :

1. Le nouveau SW s'installe et **reste en `waiting`** — pas de `skipWaiting()` inconditionnel dans `install`.
2. Le SW n'appelle `skipWaiting()` que sur réception d'un message explicite `{type:'SKIP_WAITING'}`.
3. La page écoute `updatefound` / `waiting` et affiche un bandeau discret : « Une nouvelle version est disponible » + bouton « Recharger ».
4. **Garde-fou métier** : si des fichiers sont chargés et non exportés, la bannière indique « Terminez vos exports avant de recharger » et le bouton reste actif mais sous confirmation. En complément, un `beforeunload` conditionnel.
5. Sur `controllerchange`, recharger une seule fois (garder un booléen anti-boucle).

**Contrainte de conception** : les 3 classes d'actifs sont hashées, donc **l'ancien SW continue de servir des URLs encore valides** pendant toute la session — l'utilisateur qui refuse la mise à jour ne casse rien. C'est exactement ce qu'on veut.

⚠️ **Piège coûteux** : le fichier `standard` de Bricolage (tous les axes) pèse **131 548 B, soit 3,2× l'axe `wght` seul**. Prendre systématiquement le fichier `wght`.

**woff2 ne se recompresse pas** (MESURÉ) : gzip -9 sur `outfit-latin-wght-normal.woff2` donne 32 143 B (**−0,5 %**), brotli q11 donne 32 108 B (**−0,6 %**). Le format woff2 embarque déjà Brotli. **Les octets de police sont des octets de transfert, 1:1.**

### Coût LCP et arbitrage (ESTIMÉ — calcul montré)

Total des 3 familles, axe wght + un seul poids mono :
`41 344 + 32 292 + 14 820 = 88 456 B ≈ 86,4 KiB` de transfert incompressible.

Sur une 4G lente (≈1,6 Mbit/s effectif ≈ 200 Ko/s), **86,4 KiB ≈ 430 ms** de transfert seul, hors latence — sur un budget LCP de 2 500 ms. Deux familles au lieu de trois : `41 344 + 14 820 = 56 164 B ≈ 54,8 KiB ≈ 275 ms`, soit **~155 ms regagnés et 31,5 KiB de moins**.

**Recommandation : supprimer Outfit.** Bricolage Grotesque est une variable à axe `wght` complet — elle couvre titres *et* corps de texte. Outfit, en display grotesque géométrique, fait doublon fonctionnel avec Bricolage sans apporter de contraste typographique fort (le vrai contraste vient déjà de DM Mono pour les valeurs GPS/EXIF, ce qui est justifié sur le plan métier : chiffres tabulaires, lat/lon alignés).

**Plan polices :**
- Bricolage Grotesque Variable (wght, latin) → titres + corps — 40,4 KiB
- DM Mono 400 (latin) → coordonnées, valeurs EXIF — 14,5 KiB
- `font-display: swap` + `<link rel="preload">` sur ces deux fichiers uniquement
- Metrics-based fallback (`size-adjust`, `ascent-override`) pour éviter le CLS au swap

### Subsetting au build

**Le plus simple : ne pas le faire soi-même.** L'API Fonts d'Astro (stable depuis **Astro 6**, DOCUMENTÉ, [guides/fonts](https://docs.astro.build/en/guides/fonts/)) le couvre, avec un point décisif pour notre contrainte zéro-tiers :

> « The Fonts API focuses on performance and privacy by **downloading and caching fonts so they're served from your site**. This can avoid sending user data to third-party sites. »

Les fichiers sont « copied to the `_astro/fonts` output directory ». Providers supportés : `local`, `fontsource`, `google`, `bunny`, `adobe`, `fontshare`, `npm`. Elle génère aussi les `<link rel="preload">` et les **fallbacks optimisés** (`optimizedFallbacks`, actif par défaut, désactivable) — soit exactement le travail anti-CLS.

Configuration cible :
```js
import { defineConfig, fontProviders } from "astro/config";
export default defineConfig({
  site: "https://geotagor.xx",
  fonts: [
    { provider: fontProviders.fontsource(), name: "Bricolage Grotesque",
      cssVariable: "--font-display", weights: ["200 800"], subsets: ["latin"] },
    { provider: fontProviders.fontsource(), name: "DM Mono",
      cssVariable: "--font-mono", weights: [400], subsets: ["latin"] },
  ],
});
```

⚠️ **NON VÉRIFIÉ** : si le provider `fontsource` télécharge au moment du build, le build CI a besoin d'un accès réseau, et le build devient non reproductible hors ligne. *Pour vérifier : lancer un build avec le réseau coupé et observer.* **Repli sûr et recommandé pour un projet à contrainte forte : `fontProviders.local()` avec les deux `.woff2` versionnés dans le dépôt** (55 KiB au total, parfaitement acceptable en Git) — build hermétique, zéro requête réseau au build comme au runtime.

Si un subsetting plus agressif s'avère nécessaire (le latin complet est plus large que le français), outils vérifiés (MESURÉ, npm) :

| Outil | Version | Licence | Note |
|---|---|---|---|
| `subset-font` | 2.5.0 | **BSD-3-Clause** | « subset of a TTF/WOFF/WOFF2 font using the wasm build of harfbuzz/hb-subset » — **Node pur, pas de Python** ✅ |
| `glyphhanger` | 6.0.0 | MIT | plus haut niveau, mais dépend de fonttools/Python |
| `fontkit` | 2.0.4 | MIT | moteur de police |
| `harfbuzzjs` | 1.4.0 | MIT | HarfBuzz compilé wasm |

→ **`subset-font` répond à la question « existe-t-il un outil Node ? » : oui, et sa licence BSD-3-Clause est conforme.** fonttools/Python n'est pas nécessaire.

## 6. Web Worker + WASM

Tout est documenté côté Vite ([vite.dev/guide/features](https://vite.dev/guide/features.html), DOCUMENTÉ), et Astro 7 embarque Vite 8.

**Worker de type module — syntaxe recommandée par la doc :**
```js
const worker = new Worker(new URL('./exif.worker.js', import.meta.url), { type: 'module' })
```
> « Compared to the worker suffixes, this syntax leans closer to the standards and is the **recommended** way to create workers. »
>
> « The worker script can also use ESM `import` statements instead of `importScripts()`. **Note**: During development this relies on browser native support, but for the production build it is compiled away. »

C'est le point clé : **au build, Vite compile les modules workers**, donc pas de dépendance au support natif des module workers en production. Alternatives : `import W from './w?worker'` et `?worker&inline`.

**WASM en lazy sans requête tierce — deux formes documentées :**
```js
// (a) initialiseur généré
import init from './exif_core.wasm?init'
init({ imports: { /* ... */ } }).then(instance => instance.exports.read())

// (b) contrôle total — recommandé ici
import wasmUrl from './exif_core.wasm?url'
const { instance } = await WebAssembly.instantiateStreaming(fetch(wasmUrl))
```

**Recommandation : forme (b)**, avec `import()` dynamique du module qui la contient, pour que le `.wasm` ne soit demandé qu'au premier fichier déposé. `wasmUrl` est réécrite par Vite en URL locale hashée sous `_astro/` → **servie depuis notre domaine, contrainte zéro-tiers respectée**. `instantiateStreaming` exige `Content-Type: application/wasm` — Cloudflare le sert correctement d'après l'extension, mais **à vérifier** (contrôle post-déploiement), avec repli `WebAssembly.instantiate(await (await fetch(url)).arrayBuffer())` si besoin.

**Chaîne de replis (3 niveaux) :**

| Panne | Détection | Repli |
|---|---|---|
| `Worker` indisponible | `typeof Worker === 'undefined'` | exécuter le noyau EXIF sur le thread principal, par lots avec `yield` (`scheduler.yield()` / `setTimeout 0`) pour préserver l'INP ≤ 200 ms |
| WASM refusé (CSP, plateforme) | `typeof WebAssembly === 'undefined'` | noyau JS (`exifr` 7.1.3 MIT lecture + `piexifjs` 1.0.6 MIT écriture) — **MESURÉ, licences conformes** |
| `instantiateStreaming` échoue | `try/catch` | `WebAssembly.instantiate(arrayBuffer)`, puis noyau JS si échec à nouveau |

Le noyau JS doit être un **chunk séparé chargé à la demande**, jamais dans le bundle initial — sinon on paie les deux implémentations sur le budget 150 Ko.

⚠️ **NON VÉRIFIÉ** : le poids réel du WASM issu de `little_exif`, et donc le respect du budget 400 Ko compressé. C'est l'objet du spike, hors périmètre R5. *Pour vérifier : `cargo build --release --target wasm32-unknown-unknown` + `wasm-opt -Oz` + mesure gzip/brotli avec le script du §7.*

## 7. Contrôles au build

### API `node:zlib` — signatures vérifiées (MESURÉ, exécuté sur node v22.22.2)

```
typeof zlib.gzipSync            === 'function'   ✅
typeof zlib.brotliCompressSync  === 'function'   ✅
zlib.constants.BROTLI_PARAM_QUALITY   = 1
zlib.constants.BROTLI_MAX_QUALITY     = 11
zlib.constants.BROTLI_PARAM_MODE      = 0
zlib.constants.BROTLI_MODE_TEXT       = 1
zlib.constants.BROTLI_PARAM_SIZE_HINT = 5
zlib.constants.Z_BEST_COMPRESSION     = 9
```

⚠️ **Piège d'API** : `brotliCompressSync` prend ses options sous une clé **`params`** indexée par constantes numériques — pas `{quality: 11}`. La forme correcte, celle que j'ai utilisée pour toutes les mesures de ce rapport :

```js
import { gzipSync, brotliCompressSync, constants } from 'node:zlib';

const gz = (buf) => gzipSync(buf, { level: constants.Z_BEST_COMPRESSION }).length;
const br = (buf) => brotliCompressSync(buf, { params: {
  [constants.BROTLI_PARAM_QUALITY]:   constants.BROTLI_MAX_QUALITY, // 11
  [constants.BROTLI_PARAM_MODE]:      constants.BROTLI_MODE_TEXT,
  [constants.BROTLI_PARAM_SIZE_HINT]: buf.length,
}}).length;
```

`BROTLI_PARAM_SIZE_HINT` améliore légèrement le ratio quand la taille est connue à l'avance — gratuit, autant le passer.

### Le point d'accroche : `astro:build:done`

Signature vérifiée (DOCUMENTÉ, [integrations-reference](https://docs.astro.build/en/reference/integrations-reference/)) :

```ts
'astro:build:done'?: (options: {
  pages: { pathname: string }[];
  dir: URL;
  assets: Map<string, URL[]>;
  logger: AstroIntegrationLogger;
}) => void | Promise<void>;
```

Une intégration locale (~80 lignes, zéro dépendance) qui `throw` dans ce hook fait échouer le build — c'est le mécanisme natif, préférable à un script `postbuild` npm (qui, lui, ne bloque pas si on oublie le `&&`).

Autres hooks disponibles : `astro:config:setup`, `astro:build:start`, `astro:build:setup`, `astro:build:generated`, `astro:build:ssr`.

### Les 7 contrôles à câbler

| # | Contrôle | Seuil | Méthode |
|---|---|---|---|
| **1** | Longueur des `<title>` | **≤ 60 car.** | parse `dist/**/*.html`, regex `<title>([^<]*)</title>`, décoder les entités HTML avant de compter |
| **2** | Longueur des `<meta name="description">` | **≤ 155 car.** | idem sur l'attribut `content` |
| **3** | Budget JS | **≤ 150 Ko gzip**, hors `index/*` et contours | somme `gz()` de `dist/_astro/*.js` avec liste d'exclusion explicite |
| **4** | Budget WASM | **≤ 400 Ko** compressé | `br()` sur `dist/**/*.wasm` |
| **5** | Zéro domaine tiers | 0 occurrence | regex `https?://(?!geotagor\.xx)` sur tout `dist/**/*.{html,js,css}` — **le garde-fou le plus important du projet** |
| **6** | Nombre de fichiers | **< 18 000** (marge sous les 20 000 Free) | comptage récursif de `dist/` |
| **7** | Taille max par fichier | **< 25 MiB** | `statSync` sur chaque fichier |

Contrôles complémentaires recommandés : présence d'un `schema.org` **`SoftwareApplication` et d'aucun autre type** (contrainte projet), présence de `_headers` dans `dist/`, et validation que chaque page rend son contenu principal **sans JS** (le HTML statique doit contenir le texte indexable — vérifiable en cherchant des marqueurs de contenu dans le HTML brut).

Pour le parsing HTML, **éviter les regex sur du HTML arbitraire** au-delà de `<title>`/`<meta>` : utiliser `node-html-parser` ou `cheerio` (MIT) en devDependency — **NON VÉRIFIÉ, je n'ai pas contrôlé leurs versions/licences actuelles**.

Enfin, un rapport lisible à chaque build (`logger.info`) listant chaque chunk avec brut/gzip/brotli : c'est ce qui rend le budget *vivant* plutôt qu'un contrôle binaire qu'on finit par contourner.
